# SCRUM-15, SCRUM-26 y SCRUM-22 — Backend

Implementación basada en los tres títulos del backlog suministrado. Se amplían
las rutas existentes; no se modifica frontend ni se necesita una migración nueva.
Se presupone instalado el esquema actual y las migraciones anteriores.

## SCRUM-15: Ver historial de compras

`GET /api/clientes/:id/compras`

Requiere Bearer token y rol VENDEDOR, ADMINISTRADOR o DUENO. Administrador/dueño
consultan todas las compras del cliente; el vendedor solo ve las que él registró,
de acuerdo con la autorización ya usada por ventas y comprobantes. El cliente
puede estar inactivo; un cliente inexistente o eliminado responde 404.

Parámetros opcionales:

| Parámetro | Valores |
| --- | --- |
| `fechaInicio`, `fechaFin` | AAAA-MM-DD, inclusive; máximo 366 días si se indican ambos |
| `estado` | TODAS (predeterminado), CONFIRMADA o ANULADA |
| `pagina`, `limite` | Paginación existente: página 1–10000, límite 1–500 |

Ejemplo: `/api/clientes/8/compras?estado=CONFIRMADA&pagina=1&limite=20`.

Respuesta: `{ exito: true, datos: { compras: [...], paginacion: { pagina, limite, hayMas } } }`.
Cada compra incluye número de venta, vendedor, fecha, estado, subtotal, descuento,
total, métodos de pago, `clienteId`, `items` y `comprobanteUrl`.
Los items conservan nombre, SKU, cantidad y precio registrados en la venta.
Se cargan por página sin truncamiento por GROUP_CONCAT y sin una consulta por venta.
Un historial vacío responde 200 con arreglo vacío. Los filtros del cliente nunca
permiten sustituir el cliente de la ruta ni la identidad del vendedor autenticado.

## SCRUM-26: Aplicación de descuentos

Se ajusta `POST /api/ventas`; no se crea una segunda ruta para aplicar descuentos
ni se modifican importes de ventas confirmadas.

Ejemplos de campos en el cuerpo de venta:

```json
{ "tipoDescuento": "PORCENTAJE", "valorDescuento": 12.5 }
```

```json
{ "tipoDescuento": "VALOR_FIJO", "valorDescuento": 2500 }
```

- Sin descuento: omitir ambos campos o usar tipo null y valor 0.
- Se aplica una sola modalidad al subtotal completo, usando precios de MySQL.
- Porcentaje entre 0 y 100; valor fijo no negativo y no superior al subtotal.
- Máximo dos decimales. Servicio y modelo también validan llamadas internas:
  no aceptan tipos desconocidos, negativos, cadenas, infinitos o fracciones de centavo.
- Cálculo en centavos, redondeando medio centavo hacia arriba.
- Se conserva la regla existente de total positivo: un descuento que deje la
  venta en cero se rechaza. No se admiten ventas gratuitas con el esquema de pagos actual.
- El descuento queda en la venta y se refleja en comprobante, pago y cambio.
  Un fallo revierte venta, pago y stock. Los importes de detalle son anteriores
  al descuento global, que aparece desglosado en el encabezado del comprobante.

## SCRUM-22: Generación de comprobante

Se conserva `GET /api/ventas/:id/comprobante` con el JSON habitual y se agrega
representación HTML autónoma e imprimible, generada íntegramente por el backend.

| Solicitud | Resultado |
| --- | --- |
| Sin parámetros o `?formato=json` | JSON existente, con `datos.comprobante` |
| `?formato=html` | Documento HTML para visualizar/imprimir |
| `?formato=html&descargar=true` | Descarga `comprobante-ID.html` |
| `?formato=json&descargar=true` | Descarga `comprobante-ID.json` |

Ambos formatos requieren el mismo Bearer token y permiso sobre la venta.
El consumidor debe obtener la descarga mediante una petición autenticada;
un enlace de navegador sin token no omite la autorización.
`Content-Disposition` está expuesto mediante CORS para que el cliente pueda
leer el nombre del archivo. `descargar` admite únicamente true/false.

Incluye número de venta, fecha en America/Bogota, vendedor, cliente o consumidor
final, productos, subtotal, descuento, impuesto almacenado, total, pagos, recibido
y cambio. Las ventas anuladas muestran su estado y motivo. Los datos de producto
provienen del detalle histórico; nombre y documento del cliente y nombre del
vendedor se consultan de los registros actuales, como en el comprobante existente.

No utiliza scripts ni recursos externos. Escapa los textos variables y restringe
la política CSP de la respuesta HTML. No altera ventas, pagos ni inventario al
consultar o descargar. No implementa PDF ni facturación electrónica.

## Pruebas

- `npm test`: validación de descuentos, límites de historial, autorización,
  formato de descarga y escape de HTML.
- `npm run test:integration`: persistencia y rollback con descuentos, historial
  por cliente, estados, permisos HTTP y descarga con MySQL real.
  Usa exclusivamente una base temporal independiente, nunca DB_NAME.
